## 1. 結論

本システムでは独自ドメインを必須にしない。

初期構築では CloudFront が払い出す標準ドメインをサイト URL として使用し、独自ドメインが必要になった場合だけ追加できる設計とする。

想定 URL:

```text
https://dxxxxxxxxxxxxx.cloudfront.net
```

CloudFront 標準ドメインには HTTPS が用意されるため、独自ドメインを使わない場合、Route 53 Hosted Zone と独自ドメイン用 ACM 証明書は不要になる。

これにより、以下を削減できる。

- Route 53 Hosted Zone の固定的な月額費用
- XSERVER 側での NS 委任作業
- ACM の DNS 検証作業
- 証明書と DNS の複数リージョン管理
- 独自ドメイン導入時の初回構築手順

ただし、将来の独自ドメイン追加を妨げないよう、CDK の設定値として `domainName`、`hostedZoneId`、`certificateArn` などを任意指定できる余地を残す。

## 2. 理解したアーキテクチャ

```text
                    User Browser
                         |
                         v
                    CloudFront
                         |
            +------------+-------------+
            |            |             |
            v            v             v
           /*         /manga/*       /api/*
            |            |             |
            v            v             v
       SPA用S3      漫画用Private S3   API Gateway HTTP API
                         |             |
                  Signed Cookie        v
                  Trusted Key Group   Lambda
                                       |
                            +----------+----------+
                            |                     |
                            v                     v
                    Signed Cookie生成      Presigned PUT生成
                                                  |
                                                  v
                                      Browser -> 漫画用S3
```

### 基本方針

- SPA と API は同一 CloudFront Distribution 配下に置く。
- `/*` は認証不要の Vue SPA とする。
- `/manga/*` は CloudFront Trusted Key Group と Signed Cookie を必須にする。
- `/api/*` は API Gateway HTTP API へ転送する。
- S3 はすべて Block Public Access を有効にする。
- CloudFront から S3 へのアクセスには OAC を使用する。
- 漫画画像のバイナリは Lambda を通さず、ブラウザから Presigned PUT URL で S3 へ直接送る。
- DB、常時稼働サーバー、NAT Gateway は使用しない。

## 3. 独自ドメインを使わない場合の設計

### 3.1 CloudFront 標準ドメイン

CloudFront Distribution の `distributionDomainName` をサイト URL とする。

SPA、API、漫画画像を同じホスト名のパスで提供するため、通常利用時に不要な CORS を発生させない。

```text
https://dxxxxxxxx.cloudfront.net/
https://dxxxxxxxx.cloudfront.net/api/login
https://dxxxxxxxx.cloudfront.net/manga/work-id/001/001.webp
```

### 3.2 Signed Cookie

ログイン成功時に以下の Cookie を発行する。

```text
CloudFront-Policy
CloudFront-Signature
CloudFront-Key-Pair-Id
```

Cookie 属性は次を基本とする。

```text
Secure
HttpOnly
SameSite=Lax
Path=/
```

CloudFront 標準ドメインの場合は `Domain` 属性を付けず、host-only Cookie とする。

Custom Policy の Resource は、実際にアクセスされた CloudFront ホスト名の `/manga/*` に限定する必要がある。

API Gateway の直接 URL から偽のホスト名を送られても管理権限を取得できないよう、CloudFront 側で viewer host を上書きした専用ヘッダーとして API origin へ渡す、またはデプロイ後に確定した Distribution ドメインを安全に Lambda 設定へ反映する。

### 3.3 Presigned PUT の CORS

S3 への PUT は CloudFront ではなくブラウザから S3 へ直接行うため、漫画用 Bucket に CORS が必要になる。

許可内容は最小限とする。

```text
AllowedOrigins: https://dxxxxxxxx.cloudfront.net
AllowedMethods: PUT
AllowedHeaders: Presigned PUTで実際に使用するヘッダーのみ
```

Distribution ドメインは Distribution 作成後に確定する。Bucket の CORS から Distribution 属性を直接参照すると、Distribution が Bucket を origin として参照しているため CloudFormation の循環依存になり得る。

候補は次のとおり。

1. CDK Custom Resource で Distribution 作成後に Bucket CORS を設定する。
2. Phase 1 で CloudFront ドメインを出力し、Phase 4 導入時に設定値として再デプロイする。
3. 独自ドメイン利用時は既知の固定 Origin を通常の Bucket CORS に設定する。

実装時には、再現性を優先して Custom Resource または明示的な二段階デプロイのどちらかを選ぶ。無制限の `AllowedOrigins: *` は使用しない。

## 4. GatherModoki の先例

`D:\GatherModoki` では次の構成が実装済みだった。

- XSERVER で管理する親ドメイン配下にサブドメインを用意する。
- Route 53 でサブドメインの Public Hosted Zone を作成する。
- Hosted Zone の NS 一覧を CloudFormation Output に出力する。
- XSERVER 側で親ゾーンに NS レコードを登録し、サブドメインを Route 53 へ委任する。
- CloudFront 用 ACM 証明書を `us-east-1` に作成する。
- Route 53 に CloudFront 用 A/AAAA Alias を作成する。

- `D:\GatherModoki\infra\README.md`

漫画サイトで独自ドメインを採用する場合は、この実績のある NS 委任方式を再利用できる。ただし本システムは API も CloudFront の `/api/*` 配下にまとめるため、API Gateway 専用サブドメインと regional ACM 証明書は不要である。

## 7. 認証設計

### 7.1 閲覧認証

1. ブラウザが `POST /api/login` へ共通閲覧パスワードを送る。
2. Login Lambda が SSM Parameter Store から認証用情報を取得する。
3. タイミング差が出にくい方法でパスワードを検証する。
4. 成功時、CloudFront 秘密鍵を使って `/manga/*` 用 Custom Policy に署名する。
5. CloudFront Signed Cookie 3個を `Set-Cookie` で返す。
6. `/manga/*` Behavior は Trusted Key Group で Cookie を検証する。
7. 期限切れまたは不正 Cookie では CloudFront が 403 を返す。

パスワードそのものは保存せず、salt 付きの導出値を保存する。Node.js 標準 `crypto` の `scrypt` 等を候補とする。

### 7.2 管理認証

閲覧用パスワードと管理用パスワードは分離する。

1. `POST /api/admin/login` で管理パスワードを検証する。
2. 有効期限、用途、ランダム nonce 等を含む小さなセッション payload を作る。
3. サーバー側の管理署名鍵で HMAC 署名する。
4. HttpOnly の管理セッション Cookie として返す。
5. Presign と upload 完了 API は毎回 Cookie の署名と期限を検証する。

JWT を認証の中心にはせず、必要最小限の署名 Cookie とする。DB は使用しない。

### 7.3 秘密情報

以下は Git、CDK context、Frontend bundle に入れない。

- 閲覧パスワードの導出値
- 管理パスワードの導出値
- 管理セッション署名鍵
- CloudFront 署名用秘密鍵

低コスト要件から、SSM Parameter Store Standard の `SecureString` を第一候補とする。公開鍵は秘密情報ではないため、CDK が CloudFront Public Key に登録できる形で管理してよい。

## 8. SPA routing の注意

CloudFront Distribution 全体に対して、403 または 404 を無条件に `/index.html` の 200へ変換してはいけない。

その設定では、未認証の `/manga/*` が返した 403 まで SPA の 200へ変換される可能性がある。

代わりに、デフォルト Behavior だけへ CloudFront Function を関連付け、拡張子を持たない SPA route を `/index.html` へ書き換える。

```text
/login       -> /index.html
/work/abc    -> /index.html
/viewer/abc  -> /index.html
```

次は書き換えない。

```text
/api/*
/manga/*
/assets/*
```

## 9. Upload と metadata の考察

### Upload

- 作品フォルダを一度だけ D&D する。
- chapter と page を Natural Sort する。
- 全画像を一括 decode しない。
- 5～10程度の制限付き queue で処理する。
- 1画像ごとに decode、WebP変換、PUT、メモリ解放する。
- Presigned URL は100件程度のバッチで取得する。
- 一部失敗を記録し、失敗分だけ再試行する。

### metadata

- 全画像成功前は公開用 `metadata.json` と `index.json` を確定しない。
- Upload 中の状態は必要に応じて一時 manifest として保存する。
- 完了処理で `metadata.json` を書き、その後 `index.json` を更新する。
- `index.json` の read-modify-write は同時実行で競合し得るため、ETag を使った条件付き更新と短い再試行を検討する。

## 10. コスト考察

独自ドメインなしの基本構成では、常時稼働サーバーに相当するリソースを持たない。

主な料金は使用量ベースである。

- S3: 保存容量、PUT/GET リクエスト
- CloudFront: リクエスト、データ転送、選択する料金プラン
- API Gateway HTTP API: API 呼び出し
- Lambda: 呼び出しと実行時間
- CloudWatch Logs: 保存・取り込み量

固定的な費用になり得るもの:

- Route 53 Hosted Zone: 独自ドメイン利用時のみ
- Secrets Manager: 採用しない方針
- WAF: 必須構成としては採用しない

料金確認に利用した AWS 公式ページ:

- [Amazon CloudFront pricing](https://aws.amazon.com/cloudfront/pricing/)
- [Amazon Route 53 pricing](https://aws.amazon.com/route53/pricing/)
- [AWS Certificate Manager pricing](https://aws.amazon.com/certificate-manager/pricing/)
- [AWS Systems Manager pricing](https://aws.amazon.com/systems-manager/pricing/)
- [Amazon API Gateway pricing](https://aws.amazon.com/api-gateway/pricing/)
- [AWS Lambda pricing](https://aws.amazon.com/lambda/pricing/)
- [Amazon S3 pricing](https://aws.amazon.com/s3/pricing/)

仕様にある「月額数十円以下」は、小容量かつ低頻度利用なら目標にできるが、100,000画像を保存・閲覧する場合には保証できない。WebP後の平均が200～500KBなら画像だけで約20～50GBとなり、S3保存量と閲覧時のデータ転送量が支配的になる。

## 11. 仕様上の調整候補

### 11.1 完成条件の URL

現在の完成条件は `manga.example.com` 固定だが、ドメインを任意にするなら次へ変更する必要がある。

```text
設定されたサイトURL、またはCloudFront標準URLへアクセスできる
```

### 11.2 ACM

独自ドメインを使わない場合、CloudFront 用 ACM Certificate は作らない。

### 11.3 CORS

独自ドメインなしの場合、確定した CloudFront 標準ドメインを S3 PUT の許可 Origin に設定する手順が必要である。

### 11.4 API Gateway 直接 URL

API Gateway HTTP API の execute-api URL 自体は到達可能でも、管理 API は署名済み管理 Cookie の検証により保護する。CORS やフロントの画面制御だけを認証として扱わない。

### 11.5 料金目標

保存画像数の上限と月額数十円以下は同時に保証できない。実装後に想定保存量と閲覧量を入力できる料金表を README に掲載する。

## 12. 現時点の推奨判断

1. Phase 1 は独自ドメインなしで開始する。
2. CloudFront 標準ドメインを正規サイト URL とする。
3. Route 53 と ACM は optional configuration とする。
4. SPA、API、漫画配信を1つの CloudFront Distributionへまとめる。
5. 閲覧認証には CloudFront Signed Cookie を使う。
6. 管理 API には別パスワードと署名済み管理 Cookie を使う。
7. 秘密情報は SSM Parameter Store Standard SecureString を第一候補とする。
8. SPA fallback は CloudFront Function で限定的に行う。
9. 漫画 Bucket は必ず RETAIN とし、`cdk destroy` から保護する。
10. 実装は [`planning.md`](./planning.md) の順序で進める。
